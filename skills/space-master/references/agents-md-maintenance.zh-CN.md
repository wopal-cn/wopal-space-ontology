# AGENTS.md 维护

创建与更新项目级/目录级 `AGENTS.md` 的权威规范。这是空间内容治理的维护工作流，不是逐条任务的义务。SKILL.md 正文只路由到本文档——全部细节在此。

## 1. 更新时机

项目变更完成后，先判断是否产生了新的长期 Agent 行为边界。只有当代码、测试、配置和既有文档都无法承载该边界时，才更新项目 `AGENTS.md`。

**不更新是默认且合法的结果。** 不要为了走流程或同步本次变更而添加规则。

## 2. 语言版本与命名规则

- 用户偏好语言不是英文时，先生成偏好语言版本（如 `AGENTS.zh-CN.md`）供审核；确认后再翻译并更新正式英文版（`AGENTS.md`）。
- 偏好语言版本文件用 `AGENTS.<locale>.md` 命名；`<locale>` 采用 IETF BCP 47 / RFC 5646 语言标记。
- 正式英文版不带后缀：`AGENTS.md`；不要创建 `AGENTS.en-US.md` 之类的英文变体。
- 用户偏好语言是英文时，直接更新 `AGENTS.md`。
- 偏好语言版本的所有标题使用目标语言；禁止中英文标题混杂。
- 标题只用 Markdown 标题层级。不加章节编号（`## 1. ...`）；结构靠标题层级表达。
- `AGENTS.md` 的结构遵循本技能目录下 `templates/agent-rules.md` 模板——它是 AGENTS.md 结构的唯一真相源。

## 3. 内容边界规则

项目的 `AGENTS.md` 是 Agent 在实施、测试、验证*过程中*遵循的操作规则手册。它不是变更日志、避坑清单或实现细节复制品。

**每条规则的检验标准：** Agent 工作时需要这条指令吗？省略它会有出错风险吗？两者都成立，这条规则就属于这里——精简概括地写。

**"DESIGN 也描述了它"不是省略规则的理由。** DESIGN 承载详细描述；`AGENTS.md` 承载 Agent 不必打开 DESIGN 就必须遵循的精简操作约束。Agent 不会在每个任务里通读所有 DESIGN 文档，所以塑造日常工作的约束必须能从规则手册直达。在此概括约束并链接 DESIGN 获取细节。只有当规则对 Agent 没有任何可执行内容时才删除——绝不仅因为"DESIGN 提到这个主题"就删。

新规则必须同时满足：

- 对多个未来任务长期有效，重构后仍然为真。
- 约束 Agent 的权限、职责、行为或决策边界。
- 是 Agent 工作中必须知道并执行的——例如日志级别与内容规则、输出与路由规则、宿主/发布/DSH 操作限制、测试与验证规则、编码纪律——即使 DESIGN 详细记录了该主题。
- 写成精简的操作规则，不是 DESIGN 文字的复述；链接 DESIGN 而非复制。

以下内容不得写入 `AGENTS.md`：

- 一次性设计内容：只被某一次变更需要的具体设计决策、结构或数据模型，由 DESIGN 承载。这是核心禁令——一次性设计和单 Bug 修复不属于这里。
- 单 Bug 修复记录，以及唯一目的只是防止某个已修复 Bug 复发的规则；该约束属于测试。
- 详尽清单：目录、API 或命令编目，架构图，字段列表。
- 本次修复涉及的文件、函数、配置值、UI 结构或测试断言。
- 代码、配置、脚本、Plan 或文档中已有的描述性内容，且未附加任何操作指令。
- 只记录经验、不约束 Agent 决策的教训；那些属于长期记忆。

### 常见失败模式

边界误判会犯两个方向相反的错误：

- **过度堆砌**：记录一次性设计决策或 Bug 细节（"我遇到 X，所以要 Y"），或原样粘贴 DESIGN 细节。后来的 Agent 无法分辨长期规则和历史插曲。
- **过度裁剪**：以"DESIGN 也写了"为由删除长期操作约束。Agent 随即失去工作时必须遵循的规则，重犯同类错误。拿不准时，保留概括后的约束。

添加新规则前先合并或删除重复、过时的规则。一句话够用就不要写两句。

`AGENTS.md` 中所有文档链接必须用相对路径（相对仓库根或文档所在目录）。禁止绝对路径——这些文档会提交进 git 并跨机器共享。

头部 Canonical References 章节只承载 Agent 必须遵循的强制文档（PRD、DESIGN、业务规则）。仅参考性材料（研究、教程、辅助规范）不是规范文档，不得列在那里。一份文档要么是规范链接，要么是参考，绝不兼任。

### Code Review Rules 章节

- 代码类项目（`projects/` 下的仓库及本体仓库）的 `AGENTS.md` 必须包含 `## Code Review Rules` 章节；纯文档目录可省略。
- 新项目按模板生成该章节；更新已有 `AGENTS.md` 时该章节永久保留——禁止删除、改名、翻译标题。
- 章节内容只写方向性骨架：引用本空间实际装配的审查技能、报缺陷边界、由各项目自行填充的项目特有检查点。模板不得携带任何单个项目的具体规则。
- 所有语言版本中标题保持英文；仅正文翻译。这复用现有规则——模板定义的英文章节标题不翻译。

## 3.5 文档集一致性

更新 `AGENTS.md` 从不是孤立动作。规则必须与项目实际代码匹配，并与项目 DESIGN、PRD、README 保持一致：

- 对照代码库和权威文档逐条审计现有规则（按下文 Rule Audit 判据）；删除或修正引用代码已不存在、或约束已由结构保证的规则。
- DESIGN 或 PRD 变更时，检查 `AGENTS.md` 中与新设计矛盾过时约束，证据明确时对齐它们。
- 架构/目录表只列当前实际存在的路径；持久的目标结构约束属于 Implementation Rules，不得写成当前事实。
- 完成汇报中说明检查或对齐了哪些相关文档（DESIGN、PRD、README）。

## 4. 规则审计（任何更新之前）

**对现有 `AGENTS.md` 的更新始于审计现有规则，而不是翻译或润色。** 对照代码库和权威文档逐条审计现有规则，分类为保留/删除/修正，并在确认计划中附上审计结果。

### 删除判据（满足任一即删）

1. **引用的代码已不存在。** 规则指向的模块/文件/命令已被删除或改名。验证：`rg "<name>" <project>/src/` 无结果；`git log --all --oneline --diff-filter=D -- <path>` 显示删除提交。
2. **代码结构已自动保证该约束。** 规则针对的约束已由单一真相源（共享常量模块、生成类型、CI 检查）强制。结构保证的约束不需要 Agent 规则——规则成了噪音。
3. **它是设计细节，不是工作约束。** 规则只是复述 DESIGN 对结构、流程或数据模型的描述，对 Agent 工作时*做什么不同的事*没有任何指引；DESIGN 仍承载该描述。这比"DESIGN 提到该主题"更窄：Agent 工作中必须遵循的约束——日志级别与内容规则、输出/路由规则、宿主/发布/DSH 操作限制、测试与验证规则、编码纪律——即使 DESIGN 记录了细节也要以概括形式留在 `AGENTS.md`。删掉它，Agent 就失去了操作规则。
4. **它是纯实现事实，不是决策边界。** 描述代码做什么（读取、检查、上报），不约束 Agent 的选择。想知道这些去读代码；规则没有附加行为约束。

### 保留判据

- **安全边界**：删除范围限制、凭证单写入口、受保护内容规则。
- **行为约束**：修改时必须遵循的模式（薄 handler、输出走 OutputService、错误码约定）。
- **即使 DESIGN 覆盖该主题也保留的操作约束**：日志规则、输出与路由规则、宿主/发布/DSH 操作限制、测试与验证规则、编码纪律以概括形式留在这里。"DESIGN 写了它"不是删除理由。
- **Code Review Rules 章节**：原样保留——标题永不删除、改名或翻译；其内容照常参与审计。
- **User-Supplied Rules 章节**：永不触碰。

### 修正判据

- 目录表或命令清单与实际结构不符（目录增删、新命令域）。
- 规则与更新的权威文档或设计机制冲突（如测试分层被新设计重写）。
- 两个语言版本漂移；评审版比正式版新——双向合并，对齐到正确内容。

### 审计手段

- `rg` / `ls` 检查引用的代码路径——存在性检查。
- 项目内 `git log --oneline`——查找删除或移动了被引用模块的重构。
- 逐条对照 DESIGN 和协议文档——重复检查。
- 阅读被引用模块的实际实现——决策边界检查。

## 5. 工作流

### 步骤 1：确定目标

1. 给了路径就用路径。
2. 给了项目名，从 `.wopal-space/STRUCTURE.md` 和 `projects/` 定位候选。
3. 恰好一个项目匹配，请用户确认推断的路径。有多个精确或近似匹配，列出候选让用户选。
4. 确定目标文件：项目级用 `<project>/AGENTS.md`；目录级用 `<target-directory>/AGENTS.md`。

**输出**：目标目录、目标 `AGENTS.md` 路径、需要用户确认的路径假设。

### 步骤 2：收集上下文

优先阅读：

- 目标 `AGENTS.md` 与最近的父级 `AGENTS.md`
- `.wopal-space/STRUCTURE.md`
- 相关 DESIGN；PRD 仅在存在且未被合并进 DESIGN 时阅读；`BUSINESS_RULES.md` 仅在存在时列出
- 项目 package / build / test / typecheck / lint 配置
- 目标范围内的关键源码文件，只用于提取命令和硬约束，不做源码百科
- 提供了 `rules-context` 时一并读取

**然后对每条现有规则执行规则审计。**

WopalSpace 常见文档位置：

```text
docs/products/<name>/docs/PRD*.md
docs/products/<name>/docs/DESIGN*.md
projects/<name>/docs/DESIGN.md
<project repo>/AGENTS.md
```

**输出**：规范文档清单、现有规则摘要及审计分类（保留/删除/修正）、实现事实摘要、缺失或待确认信息。

### 步骤 3：拟确认计划

动笔前呈现完整计划并获得用户明确确认。计划必须包含：

1. 目标文件路径
2. 要引用的规范文档
3. 要写入或保留的 frontmatter `name` 和 `description`
4. 保留、新增、删除、压缩的规则摘要，附规则审计的分类
5. 移入 User-Supplied Rules 的原始规则（不适合上述章节的规则），以及拟删除的规则及理由
6. 架构/目录摘要计划
7. 开发、测试、验证要求
8. `rules-context` 的合并位置
9. 结果可能超过 300 行时的压缩或拆分策略
10. 确认 `User-Supplied Rules` 保持不变
11. 要删除或避免的低信息量内容：不存在文档的 `N/A` 占位、从 DESIGN / frontmatter / 全局规约复制的文字、冗长的目录 / API / 命令编目
12. 每个结构相关条目：当前事实、持久目标约束还是临时计划
13. 每条被删规则"为何不约束 Agent 工作"的理由——绝不允许只说"DESIGN 也覆盖了"
14. 代码项目的 `Code Review Rules` 章节的有无与内容计划（保留 / 生成 / 填充检查点）；纯文档目录确认省略是有意的

更新现有 `AGENTS.md` 时，规则和规范在初次创建后不可擅改。任何新增、修改、删除必须先作为提案出现在计划中，经用户明确确认后才能执行。

对现有 `AGENTS.md` 的小更新（不改 frontmatter、不改目标路径、不改范围、只调整 1-2 个章节），计划可压缩为：目标文件、受影响章节、保留规则、拟增删合内容、`User-Supplied Rules` 不变的确认、以及上述结构条目分类。

**输出**：等待用户确认的变更计划。

### 步骤 4：确认后动笔

1. 用户偏好语言不是英文时，先更新同目录的 `AGENTS.<locale>.md`。`<locale>` 必须用 IETF BCP 47 / RFC 5646 标记。
2. 用户确认评审版后，翻译并更新正式英文 `AGENTS.md`。正式英文版必须与确认版语义对齐。
3. 用户偏好语言是英文时，直接创建或更新 `AGENTS.md`。不要生成 `AGENTS.en-US.md` 之类的英文变体。
4. 确认之前，不得写入、覆盖或重排正式英文 `AGENTS.md`。

**输出**：更新后的评审版和/或正式版路径。

## 6. 质量清单

- [ ] 目标路径明确或安全推断
- [ ] 每条现有规则都对照代码库和权威文档审计过；审计结果呈现在计划中
- [ ] frontmatter `name` 和 `description` 存在，正文不重复 frontmatter 信息
- [ ] frontmatter `description` 单行、稳定、适合 `wopal space scan`
- [ ] 考虑过目标和父级 `AGENTS.md`（存在时）
- [ ] 存在时引用了 PRD、DESIGN 和 `BUSINESS_RULES.md`
- [ ] 不存在的规范文档不写成 `N/A` 占位
- [ ] 正文概括长期操作约束而非复制 DESIGN 文字；DESIGN 链接获取细节
- [ ] Agent 工作所需的每条长期操作约束（日志、输出/路由、宿主/发布/DSH 限制、测试与验证、编码纪律）都在场——不以"DESIGN 提到该主题"为由省略
- [ ] 无一次性设计决策或单 Bug 修复记录
- [ ] 架构章节无架构图、API 编目、命令编目或目录百科
- [ ] 架构目录表只列当前存在的路径；持久目标结构约束不写成当前事实
- [ ] 项目级文档引用子目录 `AGENTS.md` 而非复制其细节
- [ ] 文档目标 80-150 行，硬上限 300 行以内
- [ ] 基础开发/测试命令已保留
- [ ] 规则聚焦技术实现、测试与验证
- [ ] 用户偏好语言非英文时，先生成了偏好语言版本
- [ ] 规范文档以引用而非复制的方式使用
- [ ] 未从 `BUSINESS_RULES.md` 提取规则进正文
- [ ] 测试章节包含 TDD 要求，并写明哪些逻辑必须自动化测试、哪些宿主 API / 外部系统 / 真实运行时边界只能人工验证
- [ ] 偏好语言版本遵循 AGENTS 模板标题，不翻译模板定义的英文章节标题
- [ ] `User-Supplied Rules` 保持不变：无增、改、删、重排（原规范迁移除外）
- [ ] 非过时的原有规则全部保留：符合上述章节的规则归位，其余规则原样移入 User-Supplied Rules；任何被删规则在计划中有明确理由
- [ ] 完整计划在动笔前已展示并确认
- [ ] 代码项目包含 `Code Review Rules` 章节；其标题未被翻译、改名或删除
- [ ] `Code Review Rules` 章节内引用的审查技能真实存在
- [ ] 适用时，正式英文版在确认后已更新

## 7. 完成后汇报

用用户语言汇报：

1. 更新的文件路径
2. 覆盖范围
3. 关键新增/变更规则
4. 被忽略的 `rules-context` 内容及原因
5. 缺失的规范引用或假设

## 相关

- 空间访问规则（memory/REGULATIONS 写入授权）在 `REGULATIONS.md` 模板中。
- 空间组件类型（如描述 `.wopal` 的 `ontology-worktree`）定义在空间 `STRUCTURE.md`。
- 本体能力进化由 `ontology-evolution` 技能负责；`dev-flow` 只覆盖代码项目。
