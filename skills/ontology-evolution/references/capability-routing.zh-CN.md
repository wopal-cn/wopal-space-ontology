# 本体能力路由参考

本文件给进化分析提供一张紧凑的“能力组件地图”。先用 `SKILL.md` 正文的短表判断；只有 owner 交叉、归属不稳或准备正式提案时再读本文件。产品 DESIGN 只在能力体系本身的职责边界、加载机制或架构归属存在疑问时按需读取。

## 路由原则

1. **先找已有 owner。** 能修已有能力，就不要新造能力。
2. **行为放在最自然的层。** 不为了“方便注入”把工作流塞进 Agent prompt，也不为了“通用”把项目事实抬进公共池。
3. **范围尽可能低。** 只在项目成立就留项目；只在当前空间成立就留空间；只有跨空间成立才进入类型级或公共池。
4. **机制问题找机制 owner。** 缺工具、状态、自动化或运行时集成时，不要只靠提示词补丁掩盖。
5. **一份事实一个 owner。** 相同规则不要同时复制到 Agent、Rule、Skill；必要时由一个 owner 持有，其他层只引用或触发。

## 组件职责

### Agent prompt

承载角色定位、职责、决策原则、长期默认行为和稳定输出风格。

适合：角色边界错误、默认判断原则错误、长期行为应该改变。

不适合：具体工作步骤、工具 API、命令序列、按场景触发的细节规则。

### Rule

承载按条件匹配后才生效的行为约束，例如语言、框架、项目类型、Agent 专属约束。

适合：只有某类场景需要的“应该 / 不应该”。

不适合：完整工作流、确定性系统操作、空间事实。

### Skill

承载一项工作的执行流程、判断方法、验证方式和工具使用指导。它回答“这类任务怎么做”。

适合：步骤不稳定、反复绕路、验证缺失、工具选择错误、多人协作协议。

不适合：单个项目事实、Agent 人格、真正缺失的运行时能力。

### Command

承载人类给 Agent 的固定工作入口和参数语义。它描述“用户如何发起这类 Agent 工作”。

适合：稳定的 slash/agent command 入口、参数或调用契约变化。

不适合：底层确定性系统操作；后者属于 CLI / runtime owner。

### Plugin / runtime owner

承载真正的运行时能力：工具、状态、自动化、消息注入、外部系统集成、生命周期逻辑。

适合：提示词再清楚也做不到的能力缺口，或需要确定性执行的机制。

不适合：纯行为规范或流程说明。

### Assembly / archetype

承载“哪一类空间装配哪些能力”的选择，不承载能力内容本身。

适合：能力已经正确，但默认装配范围、类型组合或可见性不对。

不适合：修能力内部行为。

### REGULATIONS / project AGENTS / memory

- `REGULATIONS.md`：整个空间所有 Agent 都必须遵守的长期工作规则和安全红线。
- 项目 `AGENTS.md`：只属于某项目、且会长期影响该项目工作的开发约束与事实。
- 空间 memory：用户偏好、长期经验、避坑知识等需要按需取回的空间局部知识。

这些内容如果只在当前空间或项目成立，不应因为一次成功经验就提升进公共 ontology。

## 常见路由判断

| 现象 | 优先判断 |
|------|----------|
| Agent 总在职责边界外做决定 | Agent prompt |
| 只有特定技术栈下需要一条约束 | Rule |
| 同类任务每次执行顺序都不一致 | Skill |
| 用户需要一个稳定入口触发固定 Agent 工作 | Command |
| 缺少可调用工具、状态保存或系统集成 | Plugin / runtime |
| 某能力只该出现在 Coding 空间，不该出现在其他类型 | Assembly |
| 某项目要求所有 Git 命令必须遵循特殊约定 | 项目 `AGENTS.md` |
| 某用户长期偏好一种沟通方式 | 空间 memory / 用户档案 |

## 什么时候必须回查 DESIGN

只在以下情况读取相关设计文档，而且只读相关章节：

- 两个能力组件都看起来像 owner，现有职责边界不足以判断；
- 提案会改变能力加载、注入、装配或生命周期；
- 提案会改变 Plugin / CLI / Runtime / WopalSpace 之间的领域所有权；
- 需要新增一种能力组件或改变现有组件的定义；
- 现有 Skill 与产品设计对“谁负责什么”出现直接矛盾。

如果 DESIGN 已经明确 owner，提案遵循它；如果要改变 DESIGN 的职责边界，提案必须把设计变更列入范围，而不是只改 Skill/Prompt 绕过去。

## 防止过度进化

- 一次批评可以只是一个 `candidate`，不是一份 Proposal。
- 一个症状可能由现有能力写得不清造成，优先修 owner，不拆出新能力。
- 多个信号如果同源，合并成一个问题；不要按会话事件数量建提案。
- 没有足够证据时保留 candidate；**不出提案优于弱提案**。
