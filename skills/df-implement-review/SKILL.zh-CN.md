# df-implement-review — 代码与项目审查

## 审查回答四个问题

凡是能溜过单测、lint、类型检查和 CI 的问题，都逃不出这四类：

| | 问题 | 重点抓什么 |
|---|----------|---------|
| Q1 | 代码真把声称要做的事做成了吗？ | 空壳函数、TODO 占位、写了但没接进调用链的代码、悄悄缩水的功能 |
| Q2 | 有没有把本来正常的地方改坏？ | 函数签名没变但行为变了、外部调用点报错、共用接口被改乱 |
| Q3 | 新代码在真实输入和极端情况下对吗？ | 并发冲突、资源未释放、边界值报错、吞掉异常、安全漏洞 |
| Q4 | 测试真能兜底吗？有没有留下本次改动制造的孤儿？ | 走过场的假测试、文档与设计矛盾、本次改动留下的孤儿代码/依赖 |

## 设计是唯一的尺子

你只审一件事：**实现有没有按设计做**。设计本身好不好，不归这次评审管。

动手之前先把管辖这次改动的设计找出来：Plan 任务、DESIGN 文档条款、`AGENTS.md` 里写明的规则，或对话里明确记录过的决定。先读设计，再对着读 diff。没有 Plan 不等于没有设计——去被改区域的设计文档里找。

由此推出三条规矩，也是这份技能的核心：

1. **设计已经接受的取舍不算缺陷。** 慢但正确、轮询代替事件、一次重试而不是指数退避、缓存最多旧 60 秒——只要设计这么写了、实现也照做，就不要重新翻这个案。拿设计当标准，不要拿你脑子里的理想架构当标准。
2. **认为设计错了，说一次就停。** 写成 `Design Feedback`：指出哪条设计条款、为什么有问题、修法是先改设计。它不拦路、不算 Warning、也不许拆成一串实施缺陷。设计问题归设计负责人处理（那是 `df-proposal-review` 的活）。
3. **每条 Blocker 和 Warning 都必须写明依据。** 挂到具体的设计条款、Plan 任务或明确记录的决定上。挂不上依据的，最多算 `Info`——多数情况下它压根不该进报告。

这三条是评审效率的来源。尊重设计的评审，产出的是一份很短的偏离清单；反复重审设计的评审，产出的是一堆伪装成需求的个人偏好。

## 先选模式

开始时根据指令内容一次选定：

- **交付评审（Delivery review）**——指令带有 Plan 路径、进化提案或明确的验收标准。先对照验收标准逐条核实，再跑 Q1–Q4。
- **变更评审（Change review）**——指令只给了代码改动本身：工作区未提交修改、某个 commit、一段 commit 范围或文件列表，没有 Plan。**去找管辖被改区域的设计文档**，用它作为 Q1 的对照基准；commit 说明或背景描述只在设计留白时补位。
- **全仓瘦身与技术债审查（Repo audit）**——指令没有指定某个 diff，而是要求对整个项目或目录分析技术债、做代码体检、查死代码、查冗余依赖或查过度设计。跳过针对 diff 的 Q1–Q3，直接对全仓运行 Q4 排查（配合细则里的全仓静态扫描：排查无用依赖、孤儿文件/死导出、可用标准库替换的造轮子代码、单实现过度抽象；分析技术债时一并扫出遗留的 `TODO`/`FIXME`/`simplified:` 欠账、假测试/跳过测试和过期文档），按可削减行数从大到小输出单行清单（`- \`<tag>\` <砍什么>. <拿什么替>. [路径]`），结尾给出总账 `net: -N lines, -M dependencies possible.`（没得砍则输出 `Lean already. Ship.`）。

在变更评审里，**不要自己脑补产品需求**。业务规则由写代码的人负责，除非指令明确写了 `business_logic_review: requested`。需要产品层面拍板的疑问统一放进 `Requirement Questions`。

如果找不到任何 Plan、设计文档或已记录的决定，必须在报告里写明，并且只查 Q2、Q3 的真实缺陷。这种情况下你既没有依据判断 Q1 的交付完整性，也没有依据提改进建议。

如果指令没给任何范围说明，默认只审当前项目工作区里未提交的改动，并在报告开头写明。

指令可能附带的参数：`review_type: implementation`、`project_path`、`change_scope: working_tree`、`commit: <hash>`、`commit_range: <A>..<B>`、`background`、Plan 或提案路径、`design_docs: <path>`、`business_logic_review: requested`。

## 自动工具查过的事别重复干

单测、lint、typecheck 和 CI 已经管了"能不能编译、测试过没过、格式对不对"。再去重跑一遍纯属浪费。关于测试你只问一个问题：**万一功能坏了，这个测试真能报错吗**（Q4）——绝不是问"测试绿没绿"。

你要盯的是自动工具看不见的地方：代码是真的写完了而且接通了；没把老功能悄悄改坏；在真实使用场景下不会崩。

改动没问题就简短说没问题，马上结束。

## 怎么干：通读一遍、列三张表、定点排查

审查拖得越久，废话越多。分两步走完：

**第一步——把 diff 和改动文件读一遍，列好三张表。** 查看改动（`git diff`、`git show <hash>` 或 `git diff <A>..<B>`），边读边记三张表：

1. **交付清单**——这次改动必须做到的每一项功能或验收条件，来源是 Plan 任务、设计文档条款、`AGENTS.md` 里写明的规则，或对话里明确记录过的决定。
2. **改动接口表**——diff 动过的每一个导出函数、方法签名、数据结构（schema）、共用类型、配置项，**特别要记下那些签名没变但内部逻辑变了的函数**。
3. **可疑点表**——读代码时瞄到的可疑处：疑似没写完的空壳、没接上的调用、敷衍的断言、本次改动留下的孤儿代码。

**第二步——对着三张表跑命令核实，不回头重读。** 用 `rg`、`git diff`、`sed -n` 定点查清表里的每一项。读过的文件不要反复重读；除非接口调用链牵涉到外面的文件，否则不要去翻无关文件。查空壳、查假测试、查危险调用的命令攒成一批一次性跑完（见细则 §7 的批量排查命令）。

## Q1 — 代码真把声称要做的事做成了吗？

优先级最高。绝大多数"看着交差了、其实根本用不了"的改动都倒在这一关。

- **查空壳与占位。** 扫改动文件里的半成品：注释占位（`TODO: implement`）、敷衍文案（"coming soon"、"TBD"）、空返回（`return null`、`return {}`）、只打印日志不干活的函数、写死的假数据、空事件回调。完整清单见细则 §2。
- **查调用链有没有接通。** 新写的函数、组件、模块：在要用它的地方 import 了吗？真调用了吗？从程序入口走得通吗？查出来的数据返回给调用方了吗（还是查完就扔了）？新路由注册了吗？
- **核对承诺范围与实际改动。** 对照计划要改的文件和实际 `git diff --name-status`：答应要做的有没有漏掉？有没有夹带没声明的文件改动或偷删文件？
- **核对架构与设计规矩。** 核对改动是否遵守了该模块的成文设计约束（比如模块职责边界、`AGENTS.md` 里写明"必须"遵守的规则），以及设计明确承诺的行为。代码能跑但破了架构规矩，不算合格交付。反过来，实现里加了设计没要求的机制，那是自己加戏，不算改进——只有当它改变了设计已经钉死的行为时才需要报。

严重度：核心功能是空壳、答应交付的东西缺失、违背明确的验收标准或设计约束 → **BLOCKER**；代码写好了但没有任何地方调用它 → **WARNING**（如果"接通调用"本身就是任务要求，升为 **BLOCKER**）；未说明就删文件 → **WARNING**。有明确决策记录同意分阶段简化的，不算问题。设计没规定的地方，实现方自己选的做法就成立；如果你觉得这个留白是错的，走 `Design Feedback`。

## Q2 — 有没有把本来正常的地方改坏？

这是自动测试最容易漏掉的地方。最危险的就是：**函数参数和返回值类型都没变，编译和旧测试全绿，但函数的实际行为变了**。

- **拿出第一步记下的「改动接口表」。** 重点盯那些签名没改但内部逻辑改了的函数。
- **搜出全项目所有调用方。** 用 `rg <函数或符号名>` 搜整个项目，**尤其是本次 diff 之外的文件**。挨个看调用方：它原本依赖的前提被打破了吗？返回值多出了 `null`？同步变异步了？返回顺序变了？报错方式变了？
- **查共用测试夹具（fixture / mock）。** 如果 diff 改了共用的 mock 或测试辅助函数，看看其他用它的老测试是不是因此变成了假通过？

调用方太多时：先用 `rg -l` 列出文件，抽查有代表性的调用点，并把没查完的范围如实写进报告的 `UNCOVERED STEPS`，绝不假装全查过了。

严重度：diff 之外的调用点在具体场景下会被改崩 → **BLOCKER**；行为变了但可能是设计有意为之 → 先回去查设计条款，设计已批准的改动不算问题；查不到依据的最多写进 `Info`。

## Q3 — 新代码在真实输入和极端情况下对吗？

对着改动的代码块，按常见缺陷清单（细则 §4）逐项过一遍，不靠感觉猜：并发读写冲突、文件/连接/定时器打开后没关闭（尤其是报错分支漏关）、空数组/零值/越界、异步 `await` 漏写、catch 后把错误吞掉不处理、不安全的类型强转、安全漏洞（拼接命令/SQL、`innerHTML`、新接口漏鉴权、硬编码密钥）。

**每一条问题都必须给出具体的触发场景**——写明"当输入为 X、处于状态 Y 时，第 N 行会因为 Z 报错或算错"。拿不出具体场景的泛泛担忧不准写进报告。

设计已经接受的取舍，即使确实带来限制，也不算缺陷。轮询慢一点、缓存最多旧 60 秒、只重试一次、读写要排队——设计这么定、代码照做，这条问题就不存在。如果你认为设计选错了，那是 `Design Feedback`，不是 Q3 缺陷。

严重度：有明确触发场景、且行为未经设计批准的 bug，或安全漏洞 → **BLOCKER**；边界条件下存在隐患或公开接口缺参数校验 → **WARNING**。

## Q4 — 测试真能兜底吗？有没有留下本次改动制造的孤儿？

分三块检查（在**全仓瘦身审查 Repo audit** 模式下，只对全项目跑第三块，按能砍掉的行数从大到小排序）。

**1. 测试真能验出问题吗？** 把设计明确承诺的每项行为对应到测试文件，看测试到底断了什么言。重点抓假测试：被 `skip` 跳过的测试、自己跟自己比的循环断言、永远为真的占位断言（`expect(true).toBe(true)`）、只测"对象存在/不为 null"却不测具体结果。判断标准只有一条：**假如把业务代码改坏，这个测试会变红报错吗？** 设计要求的核心行为，其测试被跳过或纯属假断言 → **BLOCKER**；设计明确承诺过、却完全没有测试 → **WARNING**。设计从没提过的代码分支没测试，不算缺口——那是实现自由。

**2. 文档同步改了吗？** 如果改动了对外接口、数据结构（schema）、CLI 参数、配置项，或设计明确规定过的行为，用 `rg` 搜一下文档（`docs/`、`README`、`AGENTS.md`）里写它的地方，看文档有没有同步更新。文档现在与**设计**矛盾（不是与某个实现细节不一致）→ **WARNING**（若项目规范明确要求文档必须随代码同步，则升为 **BLOCKER**）。纯内部实现调整不用查文档。

**3. 孤儿代码清查（只查本次 diff 制造的）。** 每条问题只写一行：位置、砍掉什么、用什么替代。**拿不出替代方案的只算抱怨，不算有效问题。**

| 标签 | 重点抓什么 | 替代方案怎么写 |
|---|---|---|
| `delete:` | 本次改动切换调用方后留下的孤儿文件/函数/旧测试/依赖；本次改动新写进来的死代码 | 什么都不用，直接删 |
| `shrink:` | 本次改动新增的重复逻辑，本可复用既有函数，或用更短写法 | 写明复用位置，或直接给出更短写法 |

`stdlib:`、`native:`、`yagni:` 只在 Repo audit 模式下用。变更评审里提这三类，等于替实现方重新选技术方案——除非设计条款本来就这么要求，否则不报。

**diff 必查「断根与孤儿」**：只要看到 diff 里删掉了某个 `import`、函数调用或第三方包引用，必须立刻用 `rg` 搜一下全仓——看看那个被摘掉调用的旧函数、旧文件或 `package.json` 依赖是不是在生产代码里已经变成 **0 引用**了。如果是 0 引用却没把旧代码、旧单测或旧依赖一并删干净，直接定为 **WARNING**（REVISE）。

不要在变更评审里盘点历史遗留死代码、扫全仓 0 引用依赖、评估既有实现该不该改用标准库、审查已有接口是否过度抽象。这些都不是本次改动引入的，提了只会把一次小修变成重构——那是 Repo audit 的活。

绝不误伤：哪怕只有几行、只要逻辑坏了能报警的最小冒烟测试或 `assert` 自检，那是质量底线，绝不算赘肉。绝不简化掉：外部输入校验、防数据丢失的错误处理、安全检查。先保证功能对，再追求代码短。

严重度：本次改动留下了 0 引用的孤儿文件/函数/依赖，或本次新增了与既有 `file:line` 实现重复的逻辑 → **WARNING**（REVISE）；其余精简建议 → **INFO**。

总账 `net: -N lines, -M dependencies possible` 只在 **Repo audit** 模式下输出。变更评审不欠读者一个"必须砍点什么"的交代——在变更评审里找删除机会，正是一次小修变成多余重构的起点。

## 本体进化提案的落地把关

如果评审的是本体进化提案落地后的能力文件（技能、规则、agent、命令），在 Q1 基础上多查一条：

**能力规范把关。** 落地文件必须符合平台规范：frontmatter 必须有 `name` + `description`；触发条件必须写在 `description` 里，不能藏在正文深处；正文只写工作流、输出格式、注意事项，长篇细则放进 `references/`；`scripts/` 里只放可复用的确定性脚本；不准自创奇怪的目录结构。最重要的是：**`description` 和正文必须用大白话写清楚，不能堆砌黑话或模棱两可的机器腔**，让人和 AI 读一遍就知道什么时候触发、怎么一步步照做。

严重度：违反规范或满篇黑话让人没法评审 → **WARNING**（REVISE）；缺 frontmatter 或引用了不存在的文件导致根本用不了 → **BLOCKER**。

## 规模：快速评审 vs 完整评审

- **快速评审**——改动很小（约 ≤ 50 行、只改了单个文件、局部微调）：四个问题都过一遍，不翻细则，建一条 todo，输出精简版报告。
- **完整评审**——其余所有情况：每个问题建一条 todo，对照细则排查，输出完整版报告。

哪怕只有 10 行改动也绝不能跳过 Q2——改一行函数返回值，照样能弄崩外面十几个调用点。

## 怎么避免瞎报错（误报校准）

报错准不准，看你能不能忍住不报废话。以下情况一律不报：编译器/linter/测试已经管了的事；纯属个人口味的代码风格或命名偏好；"如果是我写我会换种设计"；拿不出具体出错场景的空洞担忧；不在本次评审范围内的老问题；已经明确批准的分阶段简化；设计已经拍板的取舍；保底的最小测试。**每一条 Blocker 和 Warning 都必须标出 `文件:行号`、实打实的证据（代码片段或命令输出），以及它违背的设计依据**——挂不上设计依据的最多算 `Info`，纯偏好则不写进报告。

## 设计意见怎么提（Design Feedback）

认为设计本身有问题时，说一次就停：

```
## Design Feedback
- {设计条款与路径} — {为什么有问题} — 修法是先改设计，再重新评审实现。
```

几条限制，防止它变成第二场评审：

- **不拦路。** 既不算 Blocker 也不算 Warning，不改变结论。
- **最多 2 条。** 三条以上说明你在重新设计功能，那不是这份评审的职责。
- **说设计问题，不要拆成一串下游实施缺陷。** 把一个设计选择拆成五条"风险"，就是评审自己发明范围的过程。
- **设计只是没写，不算错。** 留白时实现方的选择成立；拿需求去填留白，就是在发明需求。

## 严重逻辑风险怎么报

`Serious Logic Risks` 只服务一种情况：有 `文件:行号` 证据、后果不可逆或严重（误删数据、破坏状态、伤害用户），**并且与设计某条明确条款冲突**。这个门槛比 Q3 更严：后果要严重，而且设计没接受过它。设计明确接受过的严重后果，走 `Design Feedback`，不走这里。

## 评审效率——目标 2 轮内收敛

力求在**两轮内**（初审 + 一次复审）收敛评审：

1. **首次评审必须在设计范围内一次查透**：四个问题全部跑完，把所有能挂上设计依据的问题一次性列全，绝不挤牙膏。挂不上依据的不进报告——"边界情况"不是收编个人偏好的通行证。
2. **复审聚焦核验修复**：复审只验证已指出的修复项及直接影响面，避免在后期发散引入缺乏依据的个人偏好。

评审技能只负责实事求是呈现缺陷，不擅自设卡中断。迭代预算、熔断上限与升级用户机制属于控制工作流（如 `dev-flow`）。

## 结论与报告格式

```
PASS   — 0 个 Blocker，0 个 Warning
REVISE — 0 个 Blocker，至少 1 个 Warning
BLOCK  — 至少 1 个 Blocker
```

`Design Feedback`、`Needs Human`、`Serious Logic Risks`、`Requirement Questions` 一律不影响结论。下结论前四个问题必须全部查完；哪怕一上来就发现了 Blocker，剩下的问题也必须查完一并报出。如果中途受限于环境或预算没查完某一步，必须在 `UNCOVERED STEPS` 里如实写明。

**完整报告格式：**

```markdown
# 实施评审 — {范围名称}

## Summary
- Review type: Implementation（交付评审 | 变更评审 | 全仓瘦身审查）
- Verdict: PASS | REVISE | BLOCK
- Counts: Blocker N / Warning N / Info N / Design-feedback N / Needs-human N
- Reviewed: {Plan 路径 / commit / commit range / working tree}
- Design basis: {Plan 任务 / DESIGN.md 条款 / AGENTS.md 规则 / 已记录的决定 | 未找到}
- Lean count: {仅全仓瘦身审查：net: -N lines, -M dependencies possible | Lean already}

## Blocker
### B-01: {问题标题}
- Location: `{file}:{line}`
- Basis: {违背的设计条款、Plan 任务或明确记录的决定}
- Evidence: {代码片段或命令输出}
- Impact: {在什么具体场景下会导致什么失败}
- Fix direction: {具体怎么改——指明改法，不要只写"优化这里"}

## Warning
{同 Blocker 格式；Impact 可省}

## Info
{每条一行}

## Design Feedback
{最多 2 条；只写设计问题，不写实施缺陷；不影响结论}

## Serious Logic Risks (Discuss with User)
{仅当后果不可逆或严重、且与设计明确条款冲突时填写}

## Requirement Questions
{仅当需求本身不清楚、单靠代码无法判断对错时填写}

## Needs Human
- {事项} — 为什么必须靠人工操作或肉眼确认

## Positive Findings
- {已核实通过的要点：写明是怎么核实的}

## UNCOVERED STEPS
{仅当有步骤未能完成时如实说明}
```

**快速报告格式：** `Summary`（字段同上）+ 合并的 `Findings` 列表（标明 B/W/I）+ `Positive Findings`。

**全仓瘦身审查（Repo audit）报告格式：** 直接输出按削减体量从大到小排序的单行列表（`- \`<tag>\` <砍什么>. <拿什么替>. [路径]`），最后一行写 `net: -<N> lines, -<M> deps possible.`（或 `Lean already. Ship.`）。

判 `PASS` 时必须在 `Positive Findings` 里写明查了哪些关键点、怎么核实的——不写核实依据的空头 PASS 没有可信度。

## 下完结论之后

- **REVISE / BLOCK**：改完代码后必须经过复审才算通过。复审时接着同一个评审会话继续，确保之前查出的问题一条不漏地复核。
- **PASS**：评审结论是给主控者或用户的决策依据，不代表自动合并或自动改写任务状态。
- 审查者只管查问题，不准在审查过程中擅自动手改业务代码。
