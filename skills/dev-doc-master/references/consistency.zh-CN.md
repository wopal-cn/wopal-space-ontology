# 文档集一致性 — 通用规则

这些规则适用于产品文档集中的每一份文档：PRD、DESIGN（主与子）、Phase、AGENTS.md。它们存在的目的是让文档集保持连贯，避免重复或矛盾的陈述，并将维护成本维持在低位。

## 不编号章节

标题通过 Markdown 标题层级表达结构，而非数字。写 `## Capability Scope`，绝不写 `## 1. Capability Scope`。章节编号迫使每次插入、移动或删除都要重新编号；标题层级则能承受结构编辑。适用于每一份生成或更新的文档。

## 目标态写作

文档只描述目标态——系统是什么、存在什么、谁拥有它、它承担什么责任。禁止过程态描述：不写 "deprecated"、"legacy"、"moved from X"、"old path"、"migration"、"historical" 之类的说明。能力归他处所有时，陈述归属，而非迁移。读者阅读文档学到的是当前结构与责任，绝不是它如何演变至此的历史。

## 写作风格

目标态内容只完成一半工作；另一半是它读起来如何。以下规则适用于文档集中每份文档的每一句话。

### 自然语言

写得像一个人向同事清楚解释一件事。大声朗读这句话——如果听起来像机器产物，重写它。优先使用朴素动词与具体名词，避免名词化和堆叠修饰语。

### 一句一个想法

保持句子简短，每句只承担一个想法。当一句话包含两个独立断言时，拆开它。冗长的复合句会掩盖哪部分是承诺、哪部分是装饰。

### 肯定优于否定

陈述组件做什么、拥有什么、谁负责。不要写 "X does not handle Y" 或 "Y is not supported"，而写 "Y is owned by X" 或 "Y belongs to a later phase"。读者应该学到结构，而不是从一列缺失中重构它。

### 归属优于排除

通过归属而非排除画边界。"X is responsible for A; Y owns B" 比 "X does not do B, and Y is not involved in A" 读起来更好。每个边界陈述都要为两侧各命名一个所有者。

## 只用相对链接

所有文档链接相对于仓库根或文档所在目录。绝对路径（如 `/Users/...`、`file:///...`）被禁止，因为这些文档会提交进 git 并在多台机器间共享——绝对路径只在写下它的那台机器上有效。在文档内一致使用 `./DESIGN.md`、`../DESIGN.md` 或 `docs/products/<name>/DESIGN.md` 风格的相对路径。

## 头部 = 必须，末尾 = 参考

每份文档有两个职责不同的链接区：

- **头部**（标题后的元数据块）：只放**必须**文档——本文档必须遵循的父文档与兄弟文档。例如 PRD 的 `Related DESIGN`、子 DESIGN 的 `Parent: ./DESIGN.md`、阶段文档的 `Product PRD` + `Product DESIGN`、产品 DESIGN 的 `Sibling DESIGNs`。
- **末尾**（`Reference Documents`）：放**仅参考**文档——对本文档有参考价值但不构成约束的材料。这个名字的窄义很重要：它告诉作者，只有读者真正受益于跟随的文档才属于这里，而非仅仅因为相邻。

一份文档要么是头部必须链接，要么是末尾参考链接，绝不同时。绝不把头部文档再次列在末尾章节，也绝不把参考文档提升进头部当作约束。

### 义务测试

当文档位置不确定时，问读者是否必须跟随它才能评估本文档。

- **必须跟随** → 头部。该文档陈述了本文档受其约束的契约、约束或架构。长路径、另一个仓库、另一个团队的归属、不同的命名约定都不会削弱义务。
- **会受益** → 末尾章节。该文档提供本文档不依赖的背景、先例或外部上下文。

常见的失败是向末尾章节漂移：作者看到一份"外部感"的文档（它在另一个仓库里，或者先于本文档写成），就把它归档为参考。这会把约束性契约静默降级为可选阅读。头部是读者的依赖地图——被归档为参考的依赖，是读者会错过的依赖。

## 语言

无论文档语言如何，每份文档的标题与头部字段名都是英文。质量门脚本按字面匹配它们，且稳定的标题词汇使文档跨项目可比。

正文与头部字段值跟随文档语言。中文文档的正文与字段解释读中文；标题保持英文。

## 差距明细只有一个家

差距明细存在于项目 `GAPS.md`，再无别处。阶段文档只按标识、标题、优先级与设计指针列出其范围所关闭的差距——不复述 Current / Target / Exit。重复的差距描述会漂移分离，读者随后无法分辨哪份副本是权威的。

阶段文档只承载单个差距无法承载的内容：阶段级完成标准、范围分组、推进的能力行、范围区之间固有的能力级顺序，以及残余风险。具体 Plan 的实时状态和 Plan 级执行 DAG 分别由 Plan 与 Space Active Plan Graph 持有，不进入 Phase。

## 过程文档 vs 设计文档

文档集包含两类文档，它们与设计的关系不同：

- **设计文档**（PRD、DESIGN、Phase）*继承*：它们声明必须遵循的父文档，头部承载这些强制父文档。
- **过程文档**（GAPS）*度量偏离*：它们指名所跟踪的设计，却不成为其谱系的一部分。

这个区别对头部很重要。设计文档使用谱系字段（`Parent Architecture`、`Parent Product`、`Product Intent`）。过程文档使用 `Design Source`——它指向所度量的设计，且不声称遵循架构契约。在 GAPS 文档上写 `Parent Architecture` 会错误陈述关系，并暗示该文档不承载的义务。

因为差距度量的是已定案目标与当前现实之间的距离，`Design Source` 指向正式文档。草稿在被分析前先提升为 `Active`；见文档生命周期章节。

过程文档还携带生命周期说明。GAPS 文档声明其差距关闭后即被删除，因为读者若误以为它是永久文档，就会像维护永久文档那样维护它，让过期条目不断堆积。

## 主文档罗列其子文档

无后缀主文档是其文档树的唯一切入点。其头部必须枚举其下每一个 `DESIGN-<topic>.md` / `PRD-<topic>.md` 子文档（`Sub-DESIGNs` / `Sub-PRDs` 字段）。每个子文档头部通过 `Parent: ./DESIGN.md` 指回。这个双向索引必须与磁盘上的实际文件一致——添加或移除子文档时，两侧都要更新。头部列出的子文档是结构声明而非参考，因此绝不进入末尾章节。

## 子设计枚举是文件系统事实

头部的子文档清单是文件系统事实，不是摘要。写头部前，先 `ls` 同目录下每一个 `DESIGN-<topic>.md`。头部必须恰好枚举这些文件——不多不少。写完后，重新运行同样的列举并与头部比对。头部漏掉真实文件会破坏双向索引；头部列出不存在的文件是死链。此检查属于强制质量门的一部分。

## 伴随文档 vs 子 DESIGN

文档集包含两种截然不同的支持性文件：

- **子 DESIGN**（`DESIGN-<topic>.md`）：分解主 DESIGN 章节的架构文档。它们遵循命名约定，携带 `Parent` 链接，并在主头部 `Sub-DESIGNs` 字段中被枚举。
- **伴随文档**（如 `BRANDING.md`、`API-CONTRACT.md`）：属于文档集但不是架构分解的单一真相源文档。它们不使用 `DESIGN-<topic>.md` 命名模式，不携带 `Parent` 链接，并在主头部 `Companion Documents` 字段或文档关系表中声明。

两个方向的错误分类都是错误。把伴随文档提升进子设计枚举，是发明一个不存在的结构。把真正的子设计留在临时名称下，会让文档树的一个分支对所有信任主头部地图的读者不可见——文档存在，但没有任何东西指向它。

### 按内容分类，而非按名称

文件名记录的是它最初如何被创建，而不是它变成了什么。通过问文档做什么来分类：

1. **主 DESIGN 是否把它当作自身某个章节的阐述？** 决定性信号是主文档中的委派引用——类似 "the full protocol lives in X"、"details are in X"、"the release contract is in X" 的句子。如果主文档把自己架构的一部分交给另一个文件，那个文件就是子设计，无论它叫什么名字。
2. **它是否是一个架构关注点的唯一权威来源**（契约、协议、分层模型、子系统），而非跨切面参考表（品牌常量、业务规则编号）？前者是子设计；后者是伴随文档。

规模佐证答案。接近主 DESIGN 自身长度、或单独就会超过章节拆分准则（`design.md`，约 150 行）的支持性文档，是在承载架构——它属于子设计枚举。

被分类为子设计的文档重命名为 `DESIGN-<topic>.md`，赋予 `Parent: ./DESIGN.md`，并在主头部枚举。重命名是分类的一部分，不是独立的润色步骤：命名约定是读者一眼识别文档角色的方式。

## 文档生命周期：草稿与正式

每份设计文档要么是**草稿**，要么是**正式**文档。这个区别不是品味问题；它决定文档能否被对照现实度量。

| 状态 | 类别 | 含义 |
|---|---|---|
| `Draft` | 草稿 | 设计仍在推演；其目标态可能变化 |
| `Proposed` | 草稿 | 设计已写出但尚未定案 |
| `Active` | 正式 | 设计已定案且具有约束力 |

**只有正式文档参与 GAPS 分析。** 草稿描述的目标态仍在移动。对照它度量实现产生的差距，会被下一次修订作废，于是跟踪器充满噪音，团队学会无视它。规则直接跟随差距的含义而来：差距是定案目标与当前现实之间的距离，而草稿没有可度量的定案目标。

**草稿在分析其差距之前先成为正式。** 将文档从 `Draft` 或 `Proposed` 移到 `Active`，是声明其目标形态已定案——设计决策已作出、边界已画出、契约已定义。只有在这之后，项目 `GAPS.md` 才会对照它列出差距。

`GAPS.md` 中的 `Design Source` 因此指向正式文档。当源设计仍是草稿时，分析等待提升，而不是跟踪移动目标。

设计文档没有"已完成"状态。设计陈述系统是什么；实现进度属于 Plan 与 `GAPS.md`。设计变化时，文档就地修订并保持 `Active`。设计自身的状态描述其目标形态是否定案，绝不是它已建成多少。

## 头部字段集

每份文档头部使用来自固定词汇表的字段。字段名永远是英文，文档只用适用于它的字段——但绝不发明此集合之外的字段名。

| 字段 | 适用于 | 含义 |
|---|---|---|
| `Status` | 每份文档 | 生命周期状态：`Draft`、`Proposed`、`Active` |
| `Updated` | 每份文档 | 最后更新日期，`YYYY-MM-DD`，每次编辑刷新 |
| `Parent Architecture` | 项目 DESIGN、子 DESIGN | 本文档遵循的架构文档；产品顶层为 `N/A` |
| `Parent Product` | 项目 DESIGN、子 DESIGN | 本文档遵循的产品 PRD；无则为 `N/A` |
| `Parent` | 子文档（PRD / DESIGN / Phase） | 自身树中的直接父文档，如 `./DESIGN.md` |
| `Product Intent` | 产品 DESIGN | 该 DESIGN 遵循的 PRD |
| `Sibling DESIGNs` | 产品 DESIGN | 本产品核心子系统的项目 DESIGN；其契约约束本设计 |
| `Sub-DESIGNs` | 主 DESIGN | 其下每个 `DESIGN-<topic>.md` 的精确枚举 |
| `Sub-PRDs` | 主 PRD | 其下每个 `PRD-<topic>.md` 的精确枚举 |
| `Companion Documents` | 主 DESIGN / PRD | 伴随真相源（BRANDING、API-CONTRACT） |
| `Design Source` | GAPS | 此差距跟踪器对照度量的正式设计文档 |
| `Product PRD` | Phase | 该阶段遵循的 PRD |
| `Product DESIGN` | Phase | 该阶段遵循的 DESIGN 契约 |
| `Phase ID` | Phase | 阶段标识 |
| `Product` | Phase | 该阶段所属的产品 |
| `Scope` | 任何文档 | 标题本身有歧义时，一行收窄文档覆盖范围 |
| `Companion` | GAPS | 一行描述文档跟踪什么 |

从此表得出两条规则：

- 文档不使用不适用于它的字段。阶段文档没有 `Sub-DESIGNs`；GAPS 文档没有 `Parent Product`。
- 文档不发明字段。事实不适合词汇表时，属于正文，不属于头部。

`Parent` 与 `Parent Architecture` 是相互独立的两项义务，可以同时出现：`Parent` 指向当前树中的直接文档（`./DESIGN.md`），`Parent Architecture` 指向整个项目之上的产品级架构。它们绝不合并为一行。

## 元数据字段语义

头部元数据字段有固定含义：

| 字段 | 位置 | 含义 |
|---|---|---|
| `Status` | 全部 | 文档生命周期状态（`Draft` / `Proposed` / `Active`） |
| `Updated` | 全部 | 最后更新日期，YYYY-MM-DD，每次编辑刷新 |
| `Parent` | 子文档 | 直接父文档，项目子文档为 `./DESIGN.md` |
| `Parent Architecture` | 子文档 | 存在时，本文档必须遵循的产品级架构文档 |
| `Sub-DESIGNs` | 主文档 | 其下所有 `DESIGN-<topic>.md` 的精确枚举 |
| `Companion Documents` | 主文档 | 伴随真相源文档（BRANDING、API-CONTRACT） |
| `Reference Documents` | 末尾章节 | 仅参考材料，绝不在头部 |

子文档头部对项目父级使用 `Parent`，而非 `Parent Architecture`。`Parent Architecture` 保留给项目 DESIGN 之上的产品级文档。两者同时存在时，是目标不同的独立行。

## 强制质量门

每次文档集更新都以自动扫描收尾，在报告完成前必须通过：

1. 枚举磁盘上的 `DESIGN-*.md`，与主头部 `Sub-DESIGNs` 双向精确比对。
2. 验证每个子文档头部有 `Parent: ./DESIGN.md`。
3. 扫描绝对路径（`file:///`、`/Users/...`）——零容忍。
4. 验证相对链接解析到存在的文件——包括 Markdown 链接目标与头部字段中以反引号包裹的 `./`- 或 `../`- 前缀路径。
5. 确认末尾章节（`Reference Documents`）不含子 DESIGN 与头部文档。
6. 扫描过程态词汇（已废弃, 已放弃, 迁移, 不再执行, 历史机制, deprecated, legacy, moved from）。
7. 确认每份被触碰的文档都刷新了 `Updated` 日期。
8. 对过程文档（`GAPS.md`）：确认头部使用 `Design Source` 而非谱系字段，且头部与末尾链接不相交。

可用时运行 `scripts/verify-docset.py <docs-dir>`；否则手工运行等价的 grep 检查。扫描结果是完成报告的一部分。

## 每次更新都要做文档集一致性

更新一份文档绝不是孤立的。对任何文档的变更都可能使它的父、子、兄弟文档中的陈述失效。定稿任何更新前：

1. 识别受影响集合：父（本文档遵循的）、子（子文档）、兄弟（共享同一父级或描述同一阶段/项目的文档）。
2. 检查每个受影响文档中与本次变更矛盾的过期陈述；证据明确时修订或移除。
3. 对齐双向索引与头部链接。
4. 对齐阶段目标与 DESIGN 能力路线；对齐 DESIGN 架构与 PRD 愿景。

完成回复必须说明哪些相关文档被检查、哪些被对齐、哪些仍需跟进更新。

## 各文档类型的变更流

| 变更的文档 | 必须检查 |
|---|---|
| PRD | DESIGN（产品 + 项目）、阶段文档、子 PRD |
| 主 DESIGN | 子 DESIGN、产品 PRD、阶段文档 |
| 子 DESIGN | 分解出它的主 DESIGN 章节、PRD、阶段 |
| 阶段 / Roadmap | PRD、产品 DESIGN、项目 DESIGN、子 DESIGN |
| AGENTS.md | 项目 DESIGN、PRD、实际代码 |

## 文档角色：什么内容归哪里

项目中的每个事实恰好有一个家。作者不确定某内容该放哪份文档时，答案跟随文档的角色而来，而不是内容当前所在的位置或文件大小。

| 文档 | 承载 | 不承载 |
|---|---|---|
| PRD | 产品意图、用户问题、价值主张、范围 | 架构、模块布局、技术选型 |
| DESIGN（产品） | 系统分层、子系统边界、运行时模型、端到端流程、能力路线 | 各项目内部细节、部署机制、实施状态 |
| DESIGN（项目） | 项目角色与边界、能力范围、模块架构、技术选型、接口契约、数据与状态模型 | 另一个项目的内部细节、交付进度、任务清单 |
| DESIGN（子） | 主 DESIGN 委派的单一架构关注点——契约、协议、分层模型、子系统 | 主 DESIGN 保留的关注点、跨切面参考表 |
| 阶段 / Roadmap | 阶段目标、范围分组、按 id 关闭的差距、阶段级完成标准、能力级顺序、残余风险 | 差距明细（在 `GAPS.md`）、实施步骤与状态（在 Plan）、Plan 级执行关系（在 Active Plan Graph） |
| AGENTS.md | 代理工作时遵循的规则：命令、约定、边界、验证要求 | 架构叙事、契约定义、设计理由 |

随之而来有两个后果。

**设计内容归设计文档；操作规则归项目规范。** 部署机制——镜像布局、文件组织、回滚流程——是设计内容，存在于项目 DESIGN（或它的分发子 DESIGN）。代理部署前必须运行构建门禁的规则是工作规则，存在于 `AGENTS.md`。同一事实往往有两张面孔：DESIGN 陈述部署流水线*是什么*，`AGENTS.md` 陈述代理必须对此*做什么*。两者都写，各归其家，而不是把一份复制进另一份。

**文档按它做什么分类，绝不按它如何被命名。** 重命名是分类的一部分，不是独立的润色步骤：最终承载主 DESIGN 自身关注点的支持性文档被重命名为 `DESIGN-<topic>.md`、赋予 `Parent` 链接、并在主头部枚举。最初以临时名称写成的文档，若承载架构，它仍是子设计。

## 对齐过程的边界纪律

对齐过程让文档集符合这些规则。它不是对产品的重写。

- **修复规则管辖的事。** 元数据词汇、分类、链接完整性、章节编号、目标态语言、文档集一致性。
- **不发明决策。** 文档描述的产品状态尚未定案时，记录文档所述内容，让所有者定案。擅自挑选新范式的对齐过程超出了其授权范围。
- **先由代码与兄弟文档消解歧义。** 读仓库就能回答的问题——哪些路由被门禁、内容实际在哪里、脚本输出路径是什么——通过阅读回答，而非提问。把问题留给只有所有者能做的决策。
- **报告你发现的漂移，而非默默规范化。** 文档与代码在某个对齐过程不该单方面决定的事情上不一致时，修复明显过期的部分，报告其余部分。
