# 提案评审细则 — 分模式流程

各问题背后的完整流程。当某个问题需要完整方法、命令手册或范例时加载本文件。

**目的提醒**：本评审回答的是"照字面执行或采纳，能不能成立"。形式不归它管——dev-flow Plan 的形式归 `flow.sh plan check`，进化提案归 `wopal space evo check`，doc-master 文档集归 `scripts/verify-docset.py`。

## 1. 通读文档

跑任何命令之前，带行号通读整份文档一遍。读的过程中建好三张清单：

1. **事实**——关于仓库、系统、其他文档的每一条具体断言（数量、路径、行号锚点、文档章节、ID、命令、参数）。
2. **符号**——Plan 模式：每个反引号代码名，谁的任务用它、谁的任务创建它。文档模式：每个具名的组件、能力、契约，文档在哪里给它安排了归属。
3. **文件**——提到的每一个路径，以及它是在哪被提到的。

然后跑命令。不要在读和验之间来回切换——每回读一次，亏的比省的多。从一开始就记住文档自己声明的执行方式（顺序波次容忍同波文件重叠；声明并行的波次要求文件互斥）。

## 2. Plan 模式 — Q1：各部分拼得上吗？

只需要文档本身。读完就跑——纯机械，抓住最常见的跨任务缺陷。

### 2.1 预期文件范围（不做对账）

`## Affected Files` 表是预期足迹，不是合同；实现者在 Done 时回填实际值。**不要拿任务级文件清单对账表格。** 只剩两样可查：

1. **过期操作前提**：某行声明"创建"一个已存在的文件，或"删除"一个不存在的文件——实现者会在假前提上走错路（WARNING）。
2. **并行重叠**：声明并行执行时，波次间文件重叠是冲突（BLOCKER）。声明顺序分层时，重叠是 Plan 自己的设计——不是 finding。

**常见误报**：表格行写的是代码运行时产生的产物，不是 Plan 要写的文件——运行时产物不需要生产者。

### 2.2 符号有生产者

1. 按顺序走一遍任务。收集任务**用到**的代码名：函数调用、大写蛇形常量、导出类型、fixture、CLI 标志、环境变量。
2. 收集每个任务**声明**的名字："注册 X"、"创建 Y"、"导出 Z"。
3. 把用到的名字对到生产者：生产者存在、拼写完全一致、生产者的任务排在消费者之前。
4. 任务注册一组名字时，核对其余地方用到的每个名字都在这组里。

| 情形 | 严重度 |
|---|---|
| 用到的名字在全文找不到生产者 | BLOCKER |
| 生产者名字与消费者期望的拼写不一致 | BLOCKER |
| 生产者排在消费者后面的波次 | BLOCKER |
| 生产者存在但导出/注册位置未写明且影响接线 | WARNING |

### 2.3 每个 AC 有归属，且归对了桶

1. 列出 `### Agent Verification` 里的每条 AC。
2. 从每个 Task 的 `**Verification Intent**` 收集被引用的集合。
3. 做差集。没人引用的 AC 没有归属。跨任务 AC 必须显式标注。
4. 查归桶：测试、lint、typecheck、可脚本化的断言归 Agent Verification；只有人类观察归 User Validation。

**尚未写命令的文字判定条件**：在动手写代码前，AC 可以先用文字写清通过/失败的判定条件（具体测试命令会在编码写测试的 RED 阶段填入）。不要因为现在还是文字条件就报错；只抓那些哪怕代码写坏了也检查不出来的无效条件。

### 2.4 顺序贴着依赖

- 声明的波次/依赖顺序必须和依赖表一致：消费者不排在生产者前面。
- 声明的执行方式必须符合实际：顺序波次容忍同波重叠；声明并行的波次要求文件互斥。
- 没有任务依赖一个 Plan 从不安排创建的产物。

## 3. Plan 模式 — Q2：关于仓库的陈述是真的吗？

仓库是唯一权威。每条断言机械核查——绝不因为"看起来对"就放行。

### 3.1 命令手册

| 断言类型 | 命令 | 备注 |
|---|---|---|
| 数量（"36 个能力"） | 在真相源里数一遍 | 这个数驱动工作——必须数对 |
| 路径 / 文件名 | `test -e`、`ls`、`rg --files` | |
| 行号锚点（"`file.ts:619-669`"） | 目标版本上 `sed -n 'Np' file` | 见锚点漂移裁决 |
| 引用的文档章节 | `rg -n '^#{2,3} Section' doc.md` | 这是 Plan 的权威引用 |
| 决策 / issue ID | 在它的真相源里 `rg -n` | |
| AC 里点名的命令和参数 | 查命令存在、参数接得住 | |
| "新建" vs 既有文件 | `test -e` | |

**版本纪律**：注明每条核查对着的版本——Base Commit、worktree HEAD 或集成分支 HEAD。文档声明了 worktree 的，就在 worktree 的 HEAD 上探查，不是集成分支。

### 3.2 锚点漂移裁决

行号锚点用来定位代码，不是合同。探查锚点，顺带读前后几行：

- 落在描述的构造上，或在附近且构造清晰可辨 → 通过
- 落在不相干的代码上，或构造在别处 → WARNING
- 构造在声明版本上不存在 → 前提依赖它就是 BLOCKER，否则 WARNING

### 3.3 与权威的一致性

1. 从 Technical Context 和 `Pre-read` 列出文档点名作为依据的设计文档、规则文件、接口。
2. 确认引用的章节存在、且说的就是文档声称的意思。
3. 每条决策，在权威里找到管辖原文，比对。
4. 分歧分类：**已承认**（写明并说明理由 → 不是 finding）、**已推迟**（显式排除出范围并给理由 → 不是 finding）、**无声**（→ finding）。

裁决备注：不是文档里每句话都有约束力——老文档可能描述的是已被取代的模型。先判定对这份文档实现的模型哪份才是权威，再定冲突。

## 4. Plan 模式 — Q3：执行它能交付目标吗？

只需要文档本身（外加目标拆解——零仓库命令）。

### 4.1 目标被覆盖

把 `## Goal` 拆成独立有意义的部分；找到交付每部分的任务。没有任务的部分是意图，不是计划（BLOCKER）。

### 4.2 决策被交付

1. 每条 `D-xx`，找到实现它的任务。
2. 确认交付的就是决策陈述的范围本身。
3. 扫任务文本里的缩水词：`v1`、`简化版`、`先用静态的`、`硬编码`、`占位`、`基础版`、`最小`、`stub`、`没接到`、`先这样`。
4. 按顺序两问裁决：缩水和 Goal 或 `D-xx` 矛盾吗？`D-xx` 或范围声明**授权**它了吗？授权的缩水是分阶段交付——不是 finding。

**为什么无声缩水是 BLOCKER**：缩水的交付物到达 `verify` 时，执行预算已经花掉了。文档*说了*这是阶段就是分阶段交付，无声缩水不是。

### 4.3 AC 能失败

每条 AC：功能坏了，这条检查抓得住吗？明明要验功能行为，却只检查文件存不存在，这证明不了任何事；只把任务标题抄一遍更证明不了。抓不住错的验收条件定为 WARNING——`plan check` 脚本管格式上有没有填内容；你管填进去的条件到底能不能验出真假。

### 4.4 交接得出去

每个任务：只凭文档和声明的 `Pre-read`，合格的实现者能开工吗？

- 前置任务的接口、类型、输出是**点名**的，不是暗示的（"用 Task 2 的形状"很弱；"调用 `parseConfig(path)` 返回 `ParsedConfig`"才算就绪）。
- 任务自己的输出定义到下一个任务能消费的程度。
- `Pre-read` 列的文件存在。

只标会导致走错路的信息缺失。

## 5. Plan 模式 — Q4：Lean

对 Plan 创建的每个新东西——模块、类、接口、配置项、依赖、扩展点——按下面 6 步挨个问：

### 阶梯

1. **这东西真的需要存在吗？** 单实现接口、单产品工厂、给从不变化的值做的配置、没有消费者的扩展点、只有一个调用者的包装层。为未来瞎预留的需求 = 砍掉，一句话点出将来真遇到什么情况时再加。
2. **仓库里已经有现成的了吗？** Plan 要建的东西隔壁文件里就有。标 finding 前先用 `rg <pattern>` 搜——finding 必须写明现有实现的文件与行号（`file:line`），否则至多算 Info。
3. **标准库自带吗？** Plan 新加的依赖，语言标准库本来就能干。finding 里直接点名标准库函数。
4. **平台或运行时原生就有吗？** 代码或依赖在干平台白送的事（比如 CSS 能干的不写 JS、数据库约束能干的不在应用层手写、运行时内置 API 能干的不装包）。
5. **写法最直接吗？** 同样的功能，更短更直白的写法就能做好。finding 里给出更短写法。
6. **换新时排了拆旧吗？** 当 Plan 用新模块、新函数或新依赖替换旧方案时，必须检查是否安排了删除被淘汰的旧代码、旧单测和 `package.json` 里的旧依赖。只排"建新"不排"拆旧"，落地后一定留死代码。

### 依赖准入

Plan 里任何新增三方依赖，都需要一句明确的理由：标准库、平台原生、每个已装依赖为什么都不够用。加依赖没给理由 → WARNING。前面第 3–4 步能解决却加依赖 → WARNING，finding 直接点名该用什么。

### 严重度

| 情形 | 严重度 |
|---|---|
| 为未来瞎预留的抽象或扩展点 | WARNING |
| 重复造仓库里已有的轮子（点名 `file:line`） | WARNING |
| 标准库 / 已装包能解决却新增依赖 | WARNING |
| 替换旧方案却没排清理旧代码、旧单测或旧依赖 | WARNING |
| 同样逻辑有更短写法 | INFO |
| 风格或命名偏好 | 不是 finding |

Q4 永不 BLOCK：修法是给 Plan 瘦身，极简判断见仁见智，不是执行失败。报告 Summary 里给出总量 `net: -N lines, -M dependencies possible`；没得砍 → `Lean already`。

### 进化提案的能力门

Q1–Q4 之上，本体进化提案的交付物必须满足平台自身的能力标准：

- frontmatter 有 `name` + `description`；触发条件写在 description 里
- 正文 = 工作流、输出、注意事项；长内容下沉到 `references/`
- `scripts/` 只放确定性的、可复用的逻辑
- 不发明平台资产结构之外的多余结构

违反 → WARNING。这道门查的是**提案陈述的交付物**；落地文件由实施评审（df-implement-review）复查。

## 6. 文档模式 — D1–D4

没有任务可调度，问题换形。Q4 的名字和严重度上限沿用。

### D1 — 文档自洽吗？

读的时候找：章节间自相矛盾；术语先用后定义、或一词两用；文档引入的组件、状态、契约没有归属；某节依赖文档从未提供的上下文。

**结构合规**：文档属于 `dev-doc-master` 体系时，结构规则（header 双区、双向索引、命名、字段词汇）以 `dev-doc-master/references/consistency.md` 为准。机械部分已经被它的质量门禁（`scripts/verify-docset.py`）扫过——有就跑，把你的评审花在脚本看不见的东西上：*内容*是否配得上结构（header 指向的文档早已不再管辖这份文档、companion 被错认成 sub-design）。

| 情形 | 严重度 |
|---|---|
| 承重陈述的内部矛盾 | BLOCKER |
| 真歧义的未定义术语 | WARNING |
| 引入的组件或状态没有归属 | WARNING |
| 门禁脚本已经覆盖的结构漂移 | 只在门禁没跑时报告 |

### D2 — 关于现实的陈述是真的吗？

和 Q2 同一套机械核查（命令手册、版本纪律、锚点漂移）。文档模式追加两项：

- **兄弟文档冲突**：两份文档把同一系统说成两样。先套 3.3 的权威规则；无声分歧是 finding。
- **目标态写作**（doc-master 体系）："已废弃"、"legacy"、"原来在 X"、"迁移"这类历史叙事是 finding——读者要学的是现在的结构，不是历史。

| 情形 | 严重度 |
|---|---|
| 承重路径上被代码打脸的断言 | BLOCKER |
| 不影响决策的过期陈述 | WARNING |
| 历史叙事（doc-master 体系） | WARNING |
| 装饰性漂移 | INFO |

### D3 — 目标站得住吗？

- **可判定的目标**：旁观者分得清达没达成。"让系统更健壮"不可判定；"提交时零 schema 错误"可判定。
- **写明的边界**：文档说了自己不覆盖什么，或指了边界在哪。缺边界的文档是一张空白支票，实现者会拿去兑现。
- **需求缺口**：陈述了用户问题却没有任何需求回答它。文档的消费者会悄悄用他们自己的猜测把洞填上。
- **无声决策**：读者必须替作者做的选择，要么写明要么标记，不许埋在叙述里。

| 情形 | 严重度 |
|---|---|
| 达没达成没法判定的目标 | BLOCKER |
| 承重区域缺边界 | WARNING |
| 需求缺口（有问题无答案） | WARNING |
| 读者必须做决定的无声决策 | WARNING |

### D4 — 够精简吗？

每个功能、每一节、每个抽象都要对着目标挣到自己的位置：

- 回答不了任何已陈述问题的功能
- 给永远不会来的阶段预留的扩展点
- 模板建议但内容用不上的样板结构
- 没有读者的配置面

模板合规不是目标——结构为文档内容服务，不是反过来。严重度：与 Q4 同表（封顶 WARNING，更短写法 → INFO），适用处以 `net: -N sections possible` 代替行数。

### 文风门禁（两种模式通用）

文档的语言本身就是质量的一部分：大白话、具体、一句话一个想法、肯定式优先、用归属划边界而不是用排除。这道门抓：

- 读者要解码两遍的黑话或生造抽象名词
- 机器腔（名词化堆叠、被动语态链）
- 用否定下定义（"X 不做 Y"），而归属式（"Y 由 Z 负责"）说得更好

严重度：读者要读两遍才能懂的段落 → **WARNING**；个别别扭的句子 → **INFO**。进化提案的技能交付物标准更明确：description 和正文必须大白话、精准——agent 读一遍就知道该干什么。

## 7. 严重度校准

四档，按读者该干什么定义：

| 档位 | 含义 | 判决测试 |
|---|---|---|
| **BLOCKER** | 照字面执行或采纳会失败、违约、或缩水交付 | "这交出去，是坏的还是骗人的？" |
| **WARNING** | 能执行，但文档不安全、虚胖、含糊、或该验证的没验证 | "这会造成返工、虚胖、或藏住缺口吗？" |
| **INFO** | 值得知会的改进，无需行动 | "合理的作者会耸耸肩吗？" |
| **Unverified** | 断言在工作区里定不了案 | "我是不是没查成？" |

刻意缺席：**规模/数量阈值**。任务数、文件数、波次数、文档长度永远不是缺陷。上下文预算按任务管理；大体量的内聚文档是正常的。

### 校准演练

| 情形 | 正确裁决 |
|---|---|
| 任务引用一个没有任何任务创建的函数 | BLOCKER（Q1） |
| 任务注册 5 个错误码，后面的任务用了第 6 个 | BLOCKER（Q1） |
| 锚点 `file.ts:964` 落在 967 行的描述函数上 | 不是 finding |
| Plan 和它自己引用的设计文档矛盾，且没承认 | WARNING（Q2） |
| Plan 和设计文档矛盾，但写明"本文取代 Y 文档 §X" | 不是 finding |
| 缩到 "v1"，而 `D-04` 授权了静态层 | 不是 finding（Q3） |
| 缩到 "v1"，而 `D-04` 说"配置页展示计算出的费用" | BLOCKER（Q3） |
| Plan 加 `fast-xml-parser`，标准库没有 XML 解析器、也没装别的 | 不是 finding（Q4——第 5 级正当撑住） |
| Plan 新建工具模块，重复 `src/lib/hash.ts:12` | WARNING（Q4——第 2 级） |
| Plan 创建 `AbstractStore`，只有一个 `FileStore` 实现 | WARNING（Q4——第 1 级） |
| 设计文档 §2 说调度器管重试；§5 在 worker 里手写重试循环 | BLOCKER（D1——承重矛盾） |
| 设计文档叙述"旧单体路径已废弃" | WARNING（D2——目标态违规） |
| 设计文档目标是"改善开发者体验"，无任何可观察结果 | BLOCKER（D3——不可判定目标） |
| 提案交付物是技能，触发条件埋在第 4 节正文里 | WARNING（能力门） |
| 提案正文写"利用协同对齐层" | WARNING（文风门） |
| 缺沙箱查不成的疑虑 | `Unverified`，绝不是 finding |

## 8. 实例

### 实例 A — 符号无生产者（Q1，Plan 模式）

任务 2 注册五个错误码：`A_MISSING`、`A_INVALID`、`S_MISSING`、`S_INVALID`、`C_UNRESOLVED`。任务 4 描述失败分支"用 `TEMPLATE_MISSING` 快速失败"。

```yaml
check: Q1_symbols
severity: blocker
location: "{plan}.md:{任务 4 分支行}"
reality: "注册集合在 {plan}.md:{任务 2 行}；TEMPLATE_MISSING 不在其中"
impact: "任务 4 的失败分支照文面无法实现；实现者会即兴开第二个注册点"
fix: "把 TEMPLATE_MISSING 加进注册任务，或引用既有错误码"
```

### 实例 B — 假前提（Q2，Plan 模式）

Technical Context 断言"旧 schema 路径已不存在，初始化必然失败"。任务 4 移除该路径的读取器；AC#7 断言全仓搜索该旧标识符零命中。

在声明版本上，读取器还有一个 Plan 从未点名的存活调用点。

```yaml
check: Q2_facts
severity: blocker
```
