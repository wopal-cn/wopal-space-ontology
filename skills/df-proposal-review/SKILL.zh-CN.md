# df-proposal-review — 方案与计划评审

**你只判断一件事：照着这份方案字面执行，能不能做成、能不能达成目标、是不是用最简单直接的方式做成？**

三类文档共用这个技能，因为它们只是不同阶段上的同一件事：设计文档说"要做什么"，Plan 说"分几步怎么做"，进化提案说"怎么改一项空间能力"。它们都在动手写代码前看，也都会栽在同一个坑里——照着字面做下去，要么卡死，要么造出一堆多余的东西。

## 先选模式

看文档内容，一次选定：

- **Plan 模式** —— 文档在排任务：拆了具体步骤、先后依赖、验收条件。适用于 dev-flow Plan 和本体进化提案。
- **文档模式** —— 文档在定方案：写明目标、边界、需求、架构，还没有具体开发任务。适用于 PRD、DESIGN、子 DESIGN 等设计文档。

如果一份文档两边都有（比如带任务列表的设计文档），两个模式都跑。

## 脚本查过的格式别重复查

Plan 模式下，`flow.sh plan check` 已经自动检查过固定格式：必填字段、占位符、TDD 与 Behavior 配对、复选框格式、AC 命令是否存在、状态名是否合法。进化提案也有 `wopal space evo check`。重复查这些纯属浪费时间、制造噪音。你要查的是脚本算不出来的东西——前后步骤能不能接上、写的情况跟仓库真实代码对不对得上、所有任务加起来能不能达成总目标。

方案没问题就直说没问题，马上结束。

## 怎么干：通读一遍、列三张表、集中核实

评审拖得越久，废话越多。分两步走完：

**第一步——带行号通读全文一遍。** 边读边记下三张清单，后面的检查全靠这三张表：

1. **事实表**——文档里所有关于代码仓库、系统现状或其他文档的具体说法：数量、文件路径、行号范围、文档章节、编号（ID）、命令、参数。
2. **符号表**——每个反引号括起来的函数名/变量名/类型名（Plan 模式），或每个具名的模块/组件/能力（文档模式），记下哪个任务创建它、哪个任务调用它。
3. **文件表**——文档里出现过的每一个文件路径，以及在哪一处提到的。

**第二步——对着三张表逐一核实。** Plan 模式下：Q1 和 Q3 只看文档本身就能判；只有 Q2 需要查仓库——把要跑的命令攒成一批一次性执行。文档模式下：先看文档自身前后的逻辑和目标，再对照代码和关联文档核实真假。不要边查边回头重读整篇文档。

只做定点核实，不做大海捞针：查文件在不在用 `test -e`，看指定行号用 `sed -n 'Np'`，找章节和符号用 `rg -n`。绝不要为了核对一个小节去通读整本设计文档。一份正常规模的方案 15–25 条命令就能审完。

实在没法核实的说法放进 `Unverified`（未核实），绝不硬凑成问题（finding）。

## Plan 模式：查四个问题

| | 问题 | 重点抓什么 |
|---|---|---|
| Q1 | 前后步骤接得上吗？ | 没人创建的文件、没人定义的函数/符号、没人负责的验收项（AC）、执行顺序和依赖关系颠倒 |
| Q2 | 关于仓库现状的说法是真的吗？ | 路径已改名或不存在、行号指错地方、数量算错、跟设计文档冲突、命令根本跑不通 |
| Q3 | 做完真能达成总目标吗？ | 目标漏了没排任务、关键决定被悄悄缩水、永远不会报错的假验收项 |
| Q4 | 做法够精简吗？ | 为未来瞎预留的架子、重复造仓库里已有的轮子、多余的第三方依赖、换新忘了删旧 |

Q1–Q3 决定 Plan 能不能跑通并交差。Q4 决定它有没有过度设计——一个 Plan 就算前三关全过，也可能写得极其臃肿。Q4 发现的问题最高定为 WARNING，不单独卡死（BLOCK）。

### Q1 — 前后步骤接得上吗？

1. **每条验收项都有任务认领。** `Agent Verification` 里的每一条验收项（AC），都必须被某个 Task 的 `Verification Intent` 认领，或者明确标出是跨任务联调。顺手看一眼归类对不对：凡是能跑命令自动测的（单测、lint、类型检查）都该放在 Agent Verification，不能推给人工验收（User Validation）。
2. **用到的符号都有出处。** 后面任务调用的每一个函数名、常量名、类型名，前面必须有任务创建它，且名字拼写一模一样。比如任务 1 写"注册 5 个错误码"，任务 3 写"抛出 `TEMPLATE_MISSING`"，中间对不上号就会在实施时卡死。这是最容易抓出硬伤的一步。
3. **测试行为写得够具体。** TDD 任务里的每条 Behavior 都能直接写成一条失败测试，不用靠猜。只写一句"功能正常工作"属于没写清楚。
4. **执行顺序符合依赖关系。** 被调用的必须排在调用方前面。只有明确声明"并行执行"的任务，改同一个文件才算冲突。

**文件表只是预计改动范围，不用逐行对账。** `Affected Files` 表只是预计会碰哪些文件，不要拿每个任务里的文件列表去跟总表死磕。只抓两件事：前提搞错了（比如文件明明已经存在，却写"新建该文件"），或者声明并行执行的任务改了同一个文件。

严重度：用到的符号没人创建、名字拼错、创建者排在调用者后面、并行任务改同一文件 → **BLOCKER**。验收项没人认领、Behavior 没法写成测试、自动化检查塞进了人工验收、文件新建/删除前提搞错 → **WARNING**。

### Q2 — 关于仓库现状的说法是真的吗？

一切以仓库里的真实代码为准。文档里的每个事实说法都要跑命令核对，不能看它"写得像真的"就放过。

| 文档说法 | 怎么查 |
|---|---|
| "共有 36 个能力" | 去代码或目录里亲手数一遍 |
| "`src/x.ts` 已存在" | `test -e` |
| "`file.ts:619-669`" | `sed -n '619p'`——行号偏几行没关系，但指到完全不相干的代码就不行 |
| "DESIGN.md §3 规定了 X" | `rg -n '^#{2,3} '` 找到对应章节看原文 |
| "D-12" / "issue #45" | 去对应文档或 issue 里核对编号 |
| "运行 `flow.sh verify`" | 看脚本里有没有这个子命令和参数 |
| "新建文件 F" / "删除文件 F" | `test -e` 看现在到底有没有 |

**写明你核对的是哪个代码版本**——Base Commit、worktree HEAD 还是主分支 HEAD。如果文档指定了 worktree，就在那个 worktree 的 HEAD 上查。

接着核对它引用的上级文档（设计文档、`AGENTS.md`、现有接口定义）：找到原文比对。如果文档明确说了"这里跟原设计不同，原因是 X"，这叫合理调整；如果一声不吭就跟上级设计或规则对着干，就是违规。要是两份参考文档自己就矛盾，先分清哪一份是当前生效的权威版本。

严重度：方案立脚的前提是错的、悄悄违背安全规则、验收命令根本跑不起来 → **BLOCKER**。跟文档有出入但不影响实际开发 → **WARNING**；不影响理解的细微出入或行号小偏移 → **INFO**。

### Q3 — 做完真能达成总目标吗？

最亏的失败：每个小步骤都合格，合起来却没把正事干完。

1. **总目标没有漏项。** 把 Goal 拆成几块具体要做的事，每一块都必须有对应的 Task 去落地。
2. **既定决策没有缩水。** 每条 `D-xx` 拍板的决定，任务做出来的必须是完整效果。重点盯"v1"、"简化版"、"先写死（hardcoded）"、"先这样"这类缩水词：如果文档明确写了分阶段做，没问题；如果目标要完整版，任务里却悄悄缩水成残次品，必须揪出来。
3. **验收项真能抓出 bug。** 问一句：假如代码写坏了，这条 AC 会报错吗？不管代码对不对永远都能过的 AC 只是摆设。
4. **别人拿到就能直接动手。** 开发人员只看这份文档就能直接写代码吗？前一步任务产出的函数签名、数据结构要写清楚，不能只含糊写一句"使用上一步的结果"。只在缺了信息会导致写错代码时才报问题。

严重度：目标漏了没排任务、关键决策被悄悄缩水 → **BLOCKER**。验收项抓不住错、任务缺关键接口信息导致没法开工 → **WARNING**。文档自己明确说明的分阶段简化 → 不算问题。

### Q4 — Lean：做法够精简吗？

对 Plan 要新建的每一个东西（新模块、新类、新接口、新配置项、新依赖），按下面 6 步挨个问：

1. **这东西真的需要存在吗？** 只有一个实现类的接口、只造一种对象的工厂、永远不会改的配置项、没人调用的扩展钩子——这种"为未来预留"的架子直接砍掉，一句话说明白。
2. **仓库里已经有现成的了吗？** Plan 要新写的工具函数或模块，旁边文件里是不是已经有了？用 `rg` 搜一下，绝不让它重复造轮子。
3. **语言标准库自带吗？** 标准库几行就能干的事，不准引第三方包。
4. **平台或系统原生就有吗？** 运行时或系统原生就支持的能力，不准再包一层代码或装新依赖。
5. **写法最直接吗？** 同样的功能，能不能用更少的文件、更短更直白的结构做出来？
6. **换新时排了拆旧吗？** 如果 Plan 是用新模块、新写法或新依赖替换旧方案，必须检查它有没有安排删除被淘汰的旧文件、旧单测和 `package.json` 旧依赖——只排"建新"不排"拆旧"，落地后一定留死代码。

严重度——Q4 最高定为 WARNING：为未来瞎预留的抽象、重复造已有轮子、多余的新依赖、替换旧方案却没排清理任务 → **WARNING**（改法是给 Plan 瘦身或补上清理步骤）。同样的逻辑有更短写法 → **INFO**。完全没赘肉 → 写 `Lean already` 即可。

如果是本体进化提案，在 Q1–Q4 之外多查一条：要改的技能/规则/agent 必须符合平台规范——frontmatter 必须有 `name` 和 `description`、触发条件必须写在 description 里、正文只留工作流/输出格式/注意事项、长篇细则放进 `references/`、语言必须是大白话。违反 → **WARNING**。

## 文档模式：查四个问题

设计文档还没有拆具体任务，改查下面四件事（D4 同样最高定为 WARNING）：

| | 问题 | 重点抓什么 |
|---|---|---|
| D1 | 文档前后自洽吗？ | 前后章节自相矛盾、生造概念没解释或前后意思不一、新模块没写明归谁管 |
| D2 | 关于现状的说法是真的吗？ | 文件路径已过期、说法跟现有代码矛盾、跟关联设计文档冲突、把变更历史当现状写 |
| D3 | 目标和边界清楚吗？ | 目标没法衡量算不算完成、没划定不做哪些事、列了痛点却没对应方案、关键选择悬而未决 |
| D4 | 内容够精简吗？ | 塞了没人要的功能、为了凑模板硬填的无用章节、为遥远未来预留的复杂设计 |

### D1 — 文档前后自洽吗？

查章节之间有没有自相矛盾；专业词或自定义概念是不是没解释就直接用，或者前后意思不一致；新引入的组件、状态归哪个模块管有没有写明。如果文档属于 `dev-doc-master` 规范体系，先跑它的自动检查脚本（`scripts/verify-docset.py`）查格式，你只集中精力看内容逻辑。

严重度：核心结论前后矛盾 → **BLOCKER**；概念含糊有歧义、新组件没写明归属 → **WARNING**。

### D2 — 关于现状的说法是真的吗？

跟 Q2 一样跑命令核实：文档里凡是提到现有代码、系统行为或其他文档的地方，全部核对真伪。属于 `dev-doc-master` 体系的设计文档还必须遵守一条：**只写当前设计，不记变更历史**——正文里如果出现"已废弃"、"legacy"、"原来在 X"、"从 Y 迁移过来"这类翻旧账的叙述，直接标为问题，因为设计文档是让人看懂系统现在长什么样，不是看演变史。

严重度：关键流程上的说法跟实际代码相反 → **BLOCKER**；过期的说法但不影响核心设计决策 → **WARNING**；不影响理解的细微出入 → **INFO**。

### D3 — 目标和边界清楚吗？

目标（Goal）必须能判断"怎样才算做完"。边界（Boundary）必须写明本次不包含什么。列出来的用户痛点必须有对应的需求方案去解决——有痛点没方案，写代码的人就会自己瞎猜。需要拍板的选择必须在文档里定下来，不能含糊带过。

严重度：目标含糊到没法判断算不算完成 → **BLOCKER**；缺边界说明、有痛点无方案、关键选择没拍板 → **WARNING**。

### D4 — 内容够精简吗？

每个功能、每个章节、每层抽象都必须服务于本次目标。没人提过的多余功能、给猴年马月预留的扩展接口、为了套模板硬凑的空洞章节——统统砍掉。

严重度：与 Q4 一样，最高 **WARNING**，精简写法建议为 **INFO**。

### 语言与文风把关（两种模式通用）

文档写得像不像人话，直接决定执行会不会走样：要求用大白话、具体明确、一句话只说一件事。凡是堆砌技术黑话、生造晦涩概念、翻译腔/机器腔浓重、让人读两遍还摸不着头脑的句子，统统当作问题标出来，并直接给出大白话改法。严重度：一段话要反复琢磨才能看懂 → **WARNING**；个别句子别扭 → **INFO**。

这条规矩同样管技能（Skill）文件本身：如果提案要新建或修改一个技能，它的 `description` 和正文必须直白清楚，让人和 AI 读一遍就完全明白什么时候用、怎么用。

## 预算——每份提案最多评审 2 次

每份提案最多评审**两次**：首次评审 + 至多一次复审；复审报告即终局。

1. **首次评审必须穷尽**：所有 finding 一次性列全，包括边缘发现。藏着掖着是缺陷服务。
2. **复审 = 验证修复 + 全量重扫**：本轮发现的一切即终局——没有下一轮来补漏。

## 裁决与报告

```
PASS   — 无 Blocker，无 Warning
REVISE — 无 Blocker，至少一条 Warning
BLOCK  — 至少一条 Blocker
```

`Unverified` 永远不改裁决。

评审开始时，每个问题建一条 todo，做掉一条勾一条。四问全部过手才准裁决。预算耗尽不许装作做完：报告里显式给出 `UNCOVERED CHECKS` 节，写明什么没做、为什么。

```markdown
# 提案评审 — {提案名}

## Summary
- Review type: Proposal（Plan 模式 | 文档模式）
- Verdict: PASS | REVISE | BLOCK
- Counts: Blocker N / Warning N / Info N / Unverified N
- Verified against: {Base Commit | worktree HEAD | integration HEAD}
- Lean count: {net: -N lines, -M dependencies possible | Lean already}

## Blocker
### B-01: {问题标题}
- Location: `{文档}:{行}`
- Reality: `{文件}:{行}` 或 `{命令输出}` — {为什么这与文档矛盾}
- Impact: {执行时怎么失败}
- Fix direction: {补什么、改什么}

## Warning
{同 Blocker 格式；Impact 可省}

## Info
{每条一行}

## Unverified
- {断言} — 未能核实的原因：{原因}

## Requirement Questions
{仅当需求本身含糊、且无法从文档和代码定案时}

## Positive Findings
- {已核实项：说明怎么核实的，让读者信得过结论}

## UNCOVERED CHECKS
{仅当有检查没能完成}
```

`PASS` 必须附简短的 `Positive Findings`——查了什么、怎么查的。光秃秃的 PASS 是要读者凭信仰接受裁决。

## 裁决之后

- **`REVISE` / `BLOCK`**：修订后的文档必须复审后才算干净——没经复验的修复不是修复。复用同一个评审会话（reply），先前的 finding 还在上下文里。
- **`PASS`**：这是给评审请求方的输入，不是自动门禁。它不授权 `approve`，不替代 `plan check` 或 `evo check`，不改变执行中的状态。
- 评审不授权动手改。finding 交回文档所有者。
